Store Insight Pipeline — Engineering System Map

Visual engineering review for the Store Insight alert-card pipeline: how source data becomes signals, investigations, scored cards, and downstream feedback — plus the most practical improvements to harden identity, lineage, validation, Cortex control, replay, and closed-loop measurement.

Purpose and operating model

Store Insight turns store performance data into explainable business alert cards. Source data and YAML configuration feed detector logic; raw signals are enriched and merged into traceable candidates; investigations generate rule-based or Cortex-backed narratives; final cards are scored, validated, and written for downstream use.

Alignment check against store-insight-main

The architecture is aligned to the actual four-stage pipeline in pipeline/pipeline/pipeline.py: detect_signals() → enrich_signals() → investigate() → score() → write_alerts(). The page now uses the exact repository entry points, stage names, enabled detector families, Snowflake adapter/contracts model, and the real output table concept ALERTS_PIPELINE.

Important distinction: debug tables such as ALERT_SIGNALS_RAW, ALERT_SIGNALS_ENRICHED, ALERT_INVESTIGATIONS, and ALERT_SCORE_AUDIT are recommended future hardening tables. They are not currently written by the pipeline; current checkpointing is file-based through save_signals() / load_signals(), and final output is written through write_alerts().

End-to-end system diagram

The red tags mark the most important engineering decisions to tighten before promotion and wider operational use.

Most important product/engineering gap: the pipeline already creates useful alert cards, but without deterministic alert_id/signal_id and full run lineage, it is hard to prove whether an alert is new, continuing, rerun-created, threshold-created, Cortex-created, or actually resolved after action.

Recommended improvements shown as engineering insertion points

Prioritised from production safety and traceability first, then cost, tuning, and product feedback.
Priority Improvement Where to address Practical solution
P0 Add stable alert_id and signal_id. raw signal creation, enriched candidates, final alert table Create deterministic IDs from client, analysis date, signal type, store, department, and item/business key. Use them for rerun dedupe, lifecycle tracking, and UI action joins.
P0 Add run lineage to every output row. final alert write, replay tables, score audit Store run_id, pipeline_version, config_hash, prompt_hash, skill_file_used, engine_used, fallback_used, and source_data_watermark.
P0 Add source-data completeness checks before detection. source loading / pre-detector gate Validate current-week completeness, comparison-window completeness, store coverage, hierarchy join drop rates, non-negative commercial values, and WMD freshness. Fail safely or mark cards low confidence.
P0 Turn --deterministic into a regression test mode. pipeline invocation, CI test fixture, golden-run data For a fixed sample window, assert raw/enriched/final counts, top stores, trigger combinations, sort_value distribution, and required card fields.
P0 Fix and generalise signal merging. merge logic for OSA and non-OSA alert types Use signal-type-specific merge rules. Fix or explicitly document OSA lost-sales handling so this_week_lsv matches intended max-vs-latest behaviour.
P1 Promote validators into CI/CD gates. release workflow and target-client deployment checks Gate releases on ruff, pytest, target-client validate_views, capability validation, contract validation, and deterministic golden-run comparison.
P1 Put Cortex behind a budget and quality gate. Cortex investigation path and fallback handler Add max calls/tokens per run, retry/backoff, raw response capture, JSON validation, card quality status, and a rule-based fallback when budget or quality fails.
P1 Validate shared-session safety for parallel Cortex calls. run_pipeline_from_signals, ThreadPoolExecutor, Snowpark session usage Use a bounded Cortex queue, session-safe worker handling, or sequential Cortex execution unless parallel mode is explicitly enabled and tested.
P1 Add threshold backtesting before changing YAML values. threshold tuning workflow Compare current vs proposed thresholds for alert count, stores added/removed, alert-type mix, top-10 changes, and low-value/noisy cards.
P2 Add stage-level debug tables for replay beyond current save/load checkpointing. current save_signals/load_signals workflow plus optional Snowflake debug tables Persist ALERT_SIGNALS_RAW, ALERT_SIGNALS_ENRICHED, ALERT_INVESTIGATIONS, and ALERT_SCORE_AUDIT so investigation/scoring can be replayed independently.
P2 Add card-level validation before writing. final output writer and Cortex validation layer Reject or flag missing issue/explanation/action, generic recommendations, None/nan text leakage, invalid JSON, excessive text length, and missing facts.
P2 Make score components explainable. ranking/scoring layer and score audit table Store commercial impact, severity, trigger weight, confidence, final sort value, and a score reason for every card.
P2 Add lifecycle and post-action measurement. UI action integration, downstream analytics Track generated, seen, assigned, worked, closed, reopened, resolved, and ignored states; measure OSA, waste, and markdown KPI movement after the card is acted on.
P2 Clean up package/import setup for automation. project packaging, local development, CI Make the package installable with a standard development setup such as pip install -e . so tests and automation do not rely on fragile import paths.

Good design choices to keep

  • Externalised thresholds: YAML configuration makes threshold review and client tuning easier.
  • Detector-based signal model: signal-specific detectors keep the business logic understandable.
  • Deterministic mode: rule-based narrative generation is a strong foundation for regression testing.
  • Cortex fallback option: the split between LLM-backed and rule-backed cards is a good production-control pattern.
  • Existing validation pieces: capability, contract, view, and unit validations are already the right primitives for deployment gates.
  • Replay foundation: save_signals() and load_signals() are useful foundations for cheaper, safer debugging.

First hardening sprint

1. Traceability: add deterministic alert_id/signal_id plus run lineage columns.
2. Data safety: add completeness checks before detector execution.
3. Regression safety: turn --deterministic into a golden-run CI check.
4. Signal correctness: fix/generalise merge rules, especially OSA lost-sales handling.
5. Cortex control: add cost budget, quality validation, fallback metadata, and concurrency guardrails.

Definition of done for this diagram’s recommendations

  • Every generated alert card has a deterministic business identity and can be deduplicated across reruns.
  • Every output row can explain the exact data watermark, configuration, prompt, engine, fallback path, and pipeline version that produced it.
  • Detection does not proceed silently when this week, last week, store coverage, hierarchy, or WMD inputs are incomplete.
  • Deterministic golden-run tests catch accidental changes in detector counts, merge logic, ranking, and output shape.
  • Signal merge rules preserve facts from all relevant triggers and handle OSA lost-sales value intentionally.
  • Cortex execution has explicit budget, retry, quality, fallback, and concurrency controls.
  • Final cards are validated before write and score components are available for business explanation.
  • User action and KPI follow-up close the loop from generated recommendation to measurable store outcome.

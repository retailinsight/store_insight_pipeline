# Store Insight Alerts — MCP Server

Read-only [Model Context Protocol](https://modelcontextprotocol.io) server that
lets MCP clients (Claude Desktop, Claude web via `mcp-remote`, etc.) browse the
alert cards generated by the Store Insight pipeline and inspect the full
pipeline trace behind each card.

---

## Architecture

```
Alerts batch (pipeline/)
  └─> writes cards to SNOWFLAKE_LEARNING_DB.STORE_INSIGHT.ALERTS_PIPELINE

MCP server (this service, deployed on Railway)
  ├─> streamable-HTTP transport at  POST /mcp
  ├─> auth: X-API-Key header (STORE_INSIGHT_MCP_API_KEY)
  └─> health: GET /health            (unauthenticated)

Tools (alert data)
  list_alerts       — card-facing fields, sorted by SORT_VALUE desc
  get_alert_detail  — rendered card markdown + full signal/facts trace
  list_run_dates    — pick a RUN_DATE
  list_stores       — discover store ids
  summarise_alerts  — counts grouped by type / section / store / trigger

Tools (pipeline catalog — what the pipeline contains)
  pipeline_overview        — summary, stages, signal types
  list_signal_types        — every signal type with merge keys + counts
  get_signal_type          — full record for one signal type
  list_detectors           — every detector + problem/action/baseline/logic
  list_gatherers           — Stage-2 gatherer dispatches per signal type
  list_thresholds          — DetectorConfig fields + defaults + users
  get_investigation_skill  — narrative-engine skill markdown per signal type

Resources
  alerts://schema      — ALERTS_PIPELINE column reference + tool cheatsheet
  pipeline://reference — consolidated markdown catalog of detectors,
                         gatherers, signal fields, thresholds, skills
```

## Tools

### `list_alerts`
Card-facing browse. Returns one object per alert with `issue`, `explanation`,
`cost_if_not_fixed`, `recommended_action`, plus `type` / `section` /
`trigger_types` / `sort_value` and a synthetic `alert_id` usable as a handle
for `get_alert_detail`.

Filters: `store_id`, `run_date` (default latest), `type`
(`Availability|Compliance|Markdown|Waste`), `section`, `trigger_type` (single
token such as `WOW`, `VS_CHAIN`, `REPEAT`, `TICK_AND_FLICK`),
`min_sort_value`, `limit` (cap 500), `offset`.

### `get_alert_detail`
Returns both the rendered card and the full pipeline trace:

```jsonc
{
  "card": {
    "issue": "...", "explanation": "...",
    "cost_if_not_fixed": "...", "recommended_action": "...",
    "type": "Availability", "section": "CHILLED",
    "store_id": 408, "trigger_types": ["WOW", "VS_CHAIN"],
    "sort_value": 42.3, "run_date": "2025-06-14",
    "card_markdown": "### <issue>\n**Availability · CHILLED · Store 408**  ·  ..."
  },
  "trace": {
    "signal_json": { "signal_type": "OSA", "this_week_lsv": ..., ... },
    "facts_json":  { "osa_ppg_drilldown": [...], "osa_dow": {...}, ... },
    "llm_prompt":  "You are an OSA investigator..."
  }
}
```

Call with `alert_id` (from `list_alerts`), or the tuple
`run_date` + `store_id` + `alert_type` (+ optional `section` to disambiguate
SKU-level alerts).

### `list_run_dates`, `list_stores`
Discovery helpers.

### `summarise_alerts`
Counts + score totals grouped by `type` / `section` / `store_id` / `trigger_type`
for one `run_date`.

## Connecting from Claude Desktop

Claude Desktop currently speaks stdio-MCP, so use the `mcp-remote` bridge:

```jsonc
// %APPDATA%\Claude\claude_desktop_config.json
{
  "mcpServers": {
    "store-insight-alerts": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "https://<your-railway-domain>/mcp/",
        "--header",
        "X-API-Key:${STORE_INSIGHT_MCP_API_KEY}"
      ],
      "env": {
        "STORE_INSIGHT_MCP_API_KEY": "<your-key>"
      }
    }
  }
}
```

The trailing slash on `/mcp/` matters.

## Deploying to Railway

1. Create a new Railway service pointing at this `mcp/` directory as the root.
2. Set the following variables in the service's **Variables** tab:
   - `STORE_INSIGHT_MCP_API_KEY` — long random string.
   - `SNOWFLAKE_ACCOUNT`, `SNOWFLAKE_USER`, `SNOWFLAKE_ROLE`,
     `SNOWFLAKE_WAREHOUSE`, `SNOWFLAKE_DATABASE`, `SNOWFLAKE_SCHEMA`.
   - `SNOWFLAKE_PRIVATE_KEY_B64` (and `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` if
     the key is encrypted). See `.env.example` for the full list.
3. Deploy. Railway reads `railway.json` / `Procfile` and boots
   `uvicorn app.server:app --host 0.0.0.0 --port $PORT`.
4. Verify:
   ```powershell
   curl https://<your-railway-domain>/health
   ```
5. Point Claude Desktop at `https://<your-railway-domain>/mcp/` as shown above.

## Project structure

```
mcp/
  app/
    __init__.py
    server.py                # FastMCP server + tools + API-key middleware
    alerts_repo.py           # All Snowflake queries + card markdown renderer
    snowflake_session.py     # Cached Snowpark session (keypair or password)
    pipeline_catalog.py      # Loads pipeline_catalog.json + accessor helpers
    pipeline_catalog.json    # Generated by pipeline/tools/build_catalog.py
  .env.example
  Procfile
  railway.json
  requirements.txt
  README.md
```

The pipeline catalog (`pipeline_catalog.json`) is regenerated at dev time by
`store_insight/pipeline/tools/build_catalog.py` — see
`.windsurf/workflows/update-stages.md`.

This service is independent of `api2/` but reuses the same Snowflake
credentials pattern, so the same keypair/service account works for both.
